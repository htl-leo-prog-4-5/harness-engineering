22  The Angular app

22.1 Pin the frontend layout

The backend got its folders from AGENTS.md and a skill. The frontend has neither yet, so the agent picks a structure on every run. One run puts every file flat in src/app. Another invents a core/ folder and stops there. Each later page lands wherever that first run decided.

A structure exists already. The angular-developer skill recommends one in references/naming-conventions.md: backend access in core/, one folder per feature under features/, and reusable parts with no business logic in shared/. That file is one of about 40 references in the skill, and nothing sends the agent there. So do what you did for the backend. AGENTS.md names the folders, and the skill holds the details. Add these two bullets to the ## Layout section of ~/work/AGENTS.md, at the end:

- The frontend is one Angular application in `frontend/`. Inside
  `frontend/src/app`, the backend calls and their models live in `core/`, each
  page gets its own folder under `features/`, and components, pipes and
  directives with no business logic go in `shared/`.
- Before you create a file in `frontend/src/app`, read
  `references/naming-conventions.md` in the `angular-developer` skill and
  follow it.

The first bullet pins the folders that later commands and reviews depend on. The second one sends the agent to the file names and class names, which change with the Angular version and belong in the skill.

Commit the new bullets before you prompt:

git add AGENTS.md
git commit -m "Pin the frontend layout"

22.2 The prompt

This one prompt asks for the whole frontend, the service that talks to your backend, and a new gate stage. Most of it is ordinary scaffolding. Two bullets are not, so read them before you paste.

Add an Angular frontend to this repository.

- Create a single Angular application in a `frontend` folder. No library, no SSR,
  no PWA. Standalone and zoneless, with routing but without lazy loading.
- Styling is plain modern CSS using custom properties. Do not add Tailwind,
  Bootstrap or any other CSS framework.
- During development the frontend must reach the backend through a proxy on /api.
- One single Angular service holds every call to the backend: create, list all,
  get by id and delete for the Values entity, plus the add calculation.
- The reads that fetch stored Values (list all, get by id) use Angular's
  httpResource API. Do not write these reads as HttpClient methods that return
  an observable.
- Create and delete use HttpClient, because a resource is read-only. For the add
  calculation, pick whichever of the two fits the endpoint the backend has.
- No component calls HttpClient, httpResource or fetch itself. Components use the
  service.
- Test the service with Vitest, using Angular's HTTP testing support
  (provideHttpClientTesting and HttpTestingController).
- Add npm scripts for the tasks that matter: `start`, `build` and `test`.
- Use the latest stable versions of all npm packages.
- Do not create AI assistant config files (AGENTS.md, CLAUDE.md and similar).
  This repository already has one.
- Add a project skill in .agents/skills/api-access/SKILL.md. It documents this
  convention: where the backend calls live, which of them use httpResource and
  which use HttpClient, the development proxy, and when the file has to be
  touched.

Then add a stage to scripts/quality-gate.sh that builds the frontend for
production. Commit when the quality gate is green.

This is a hard run for a small model, harder than the quality gate was. httpResource is newer than the model’s training data, so the agent cannot write a line of the service from memory. It has to read the angular-developer skill or ask Context7 first. Expect several turns, and expect at least one of them to produce observables anyway.

22.3 One bullet names the mechanism

Every prompt in this course states outcomes and lets the agent decide how. One bullet here breaks that rule on purpose, twice in two sentences. It names httpResource for the stored-data reads. Then it names the answer you refuse to accept: an HttpClient method returning an observable.

The reason is the model, not the requirement. The model has seen the HttpClient and observable pattern thousands of times, and httpResource almost never. So “read through the modern resource API” reads to it as “make a request somehow.” What comes back then compiles and passes the gate. It shows the right numbers on the screen. So nothing you have built so far can tell you it went the wrong way.

Naming the wrong answer is the cheapest fix there is. It’s also the kind of sentence you’ll delete the day you move to a stronger model. The agent_end rule in the extension prompt is the same kind of thing: written for this model, not for the requirement.

If your agent builds more than you asked for

Some runs of this prompt produce more than scaffolding: a finished calculations page, sometimes a values page too, complete with tests. The next two chapters ask for exactly those pages. So the agent may reply “nothing to implement, everything already exists.” That’s not a problem, so keep the commit and paste the prompts anyway. Treat the chapters as review checklists for pages you already own. Every check in them still applies.

22.4 Review the skill the agent wrote

Everything except the skill bullet asks the agent for application code. The skill bullet asks it to write a piece of your harness. That’s a different kind of work, and it deserves a different kind of review.

Open .agents/skills/api-access/SKILL.md once the run is done. A useful skill states four things.

The one place requests live. It names the path of the service file, inside core/, and states the rule that goes with it: components never make a request themselves.

Which mechanism goes with which direction. Reads go through httpResource. Create and delete go through HttpClient. A resource is read-only by design, so a write cannot go through one.

When the file has to change. The next agent can recognize these situations: a backend endpoint is added, renamed, or removed; a request or response shape changes; or the port behind the proxy changes.

The failure symptom. This is what a broken binding looks like from the outside. The frontend compiles without complaint. Then the request 404s at runtime, or it succeeds and the fields come back undefined, because the TypeScript type and the C# model disagree.

The failure symptom is what separates a skill from a README. A README documents a convention. A skill describes a situation the next agent will find itself in, and it tells the agent what to do about it. So it fixes the cause, instead of debugging the symptom for half an hour.

One way to write the two parts that matter:

---
name: api-access
description: How the Angular frontend talks to the .NET backend. Every request
  goes through the single API service; reads use httpResource, create and delete
  use HttpClient, and /api is proxied to the backend in development. Use when
  adding or changing a backend call, when a backend endpoint or model changes,
  or when a request fails at runtime.
---

## Failure symptom

The frontend compiles and still gets it wrong: the request 404s, or fields come
back undefined because the TypeScript type and the C# model disagree. Nothing
before the browser or the Playwright suite catches this.

Yours names the real path of your service file. The description above leaves that open, because the agent picked the path. Compare the rest with what your agent produced, and spend most of your attention on the description. Everything under the front matter is loaded only when the agent decides the skill is relevant. The agent reads the description on every turn and uses only that field to decide whether to load the skill. If the description says “documentation about the API service,” the agent never loads the skill on the turn where it adds an endpoint. That one field is worth arguing about.

22.5 Check the wiring yourself

Start with the folders, because every later page builds on them:

find frontend/src/app -type d

No page exists yet, so core/ is the folder that matters. The service and its test sit in it. A service in src/app itself means the agent skipped the layout bullets in AGENTS.md. Send it back to them before you prompt for the first page, because that page goes under features/ and has to find the service where the layout says it is.

Three claims from the prompt are easy to verify and easy for an agent to get half right. Start with the proxy and the mechanism.

find frontend -name "proxy.conf.*" -not -path "*/node_modules/*"
grep -rn "httpResource" frontend/src

The first command finds the proxy config, because the scaffold decides where it sits: next to angular.json in some runs, under src/ in others. Open the file it prints. It has to map /api to the port the backend actually listens on. So compare it against your launch settings instead of trusting the file.

The second grep is the decisive test in this chapter. It has to hit inside the service. And the hits have to be the stored-data reads: the list and the single value. A green gate proves the frontend compiles and the service tests pass. A page that shows the right numbers proves the requests arrive. Only this grep proves the reads went through the API you asked for instead of the one the model knows better.

If the grep comes back empty, the agent built the service out of HttpClient and observables and reported success. Send it back with the same two bullets, and add that the previous attempt used observables for the reads.

The third claim is that no component makes a request of its own. Look at where the requests come from:

grep -rn "HttpClient\|httpResource\|fetch(" frontend/src/app --include=*.ts

Two kinds of line are allowed in that output. Everything from the service file is allowed, because making requests is its job. provideHttpClient() in the application config is allowed too, because it’s the registration the service needs. Anything else is a component talking to the backend on its own. The values page chapter turns this rough grep into a check worth keeping. For now, confirm that the requests all live in one file.

22.6 Look at it in the browser

cd frontend
npm start

Open http://localhost:4200 on your machine. What you get is the page Angular scaffolds by default, since nothing has been built on top of it yet. That’s the point: the toolchain runs, and the browser reaches it. Stop the server with Ctrl+C when you’re done. A dev server left running holds port 4200, and the next run fails to bind it.

Getting to that port from your host

compose.yaml publishes port 4200, so localhost:4200 in your host browser reaches the dev server inside the container. If the page doesn’t load, the dev server is listening on the container’s own loopback address only. Start it with npm start -- --host 0.0.0.0 and try again.

Port 4200 and the backend port are the only published ones. For anything else, the Ports panel in the attached VS Code window forwards a port for you. Forward a Port adds one by hand, when it doesn’t appear there by itself.
