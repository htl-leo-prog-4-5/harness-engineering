16  Persistence

16.1 When the gate grows a dependency

Every stage of the quality gate so far ran on nothing but the source tree: a formatter, a compiler, and unit tests. Hand somebody the repository and the .NET SDK. scripts/quality-gate.sh gives them exactly the verdict it gives you.

A database ends that. The backend now needs a running server before it can serve a single request, and the integration tests run against that server, so the gate needs it running too. From here on, your quality gate can go red for a reason that has nothing to do with your code.

You add this dependency on purpose. Do it now, while the project is still small. At this size, you can trace exactly what the gate needs from the environment.

16.2 Split the backend into layers

The calculator started as one API project because it had no data to look after. With a database it has rows to store and queries that belong together, and keeping those out of the endpoints is the job of a service layer. The backend grows to four projects. Calculator.Api keeps the endpoints. Calculator.Services gets the business logic, and Calculator.Persistence gets the DbContext, the entities, and the migrations. Calculator.Tests stays where it is.

The rules for that layout come in two more custom skills, from the persistence folder in ~/skill-source. Install them the same way you installed the first two:

cd ~/work
npx skills add ~/skill-source/persistence -y
ls .agents/skills/

Two new folders appear. service-layer says which project owns what, and how an endpoint calls a service. ef-core-postgres covers the EF Core side, down to the flags every dotnet ef command needs once the DbContext lives in its own project.

Installing them is only half the change. AGENTS.md still tells the agent that the backend has two projects and no class library. pi loads AGENTS.md on every turn, while a skill loads only when the agent picks it, so the old rule would win. Open ~/work/AGENTS.md and replace its ## Layout section with this one:

## Layout

- The application is called `Calculator`. The solution is
  `backend/Calculator.slnx`. Next to it sit four projects:
  `backend/Calculator.Api`, `backend/Calculator.Services`,
  `backend/Calculator.Persistence`, and `backend/Calculator.Tests`.
  `.editorconfig` stays in the repository root.
- Before you create a project or write an endpoint, load the
  `minimal-api-endpoints` skill and follow it, with `Calculator` as `{App}`.
- Before you add a service, an entity, or a migration, or run any `dotnet ef`
  command, load the `service-layer` and `ef-core-postgres` skills and follow
  them, with `Calculator` as `{App}`.
- Quality checks live in one script at `scripts/quality-gate.sh`.

The sentence that forbade a class library is gone, and the layout names four projects, because later commands in this part depend on those paths. The new third bullet tells the agent when to load the two new skills. Their one-line descriptions alone are easy for a small model to skip.

Commit the new context before you prompt, so the persistence commit holds only what the agent did:

git add AGENTS.md .agents skills-lock.json
git commit -m "Add the persistence skills and the four-project layout"

16.3 The prompt

The PostgreSQL server is already running. compose.yaml starts it as the db service. The container you work in gets the connection details as environment variables. Check them before you prompt:

printenv | grep '^PG'

Then give pi this prompt:

Add persistence to the backend.

- Use EF Core with the PostgreSQL server that already runs in this environment.
  Its connection details are in the PGHOST, PGPORT, PGDATABASE, PGUSER and
  PGPASSWORD environment variables of this container.
- Add a `Values` entity with an `Id` and two int properties named `Left` and
  `Right`. The JSON the API accepts and returns uses `left` and `right`.
- Use EF Core migrations and apply pending migrations automatically on backend
  startup.
- Add a new API module in its own file for `Values`, with: create, list all
  (ids only), get by id, and delete.
  - Get by id must also return the sum of the two values, computed with the
    existing `Add` logic.
- Then extend scripts/quality-gate.sh with a stage that fails when the entity
  model has changed but no migration covers that change. Use the command that
  EF Core ships for exactly this check,
  `dotnet ef migrations has-pending-model-changes`. It needs no database
  connection, so put the stage where it runs even when the database is down.

Look everything up in the docs. Commit when the quality gate is green.

16.4 What the prompt pins down

The prompt states outright what no documentation could tell the agent. It names the five PG environment variables, because only this container hands out its connection details that way. It pins the entity name and its two properties, down to the lowercase JSON names. And it makes get by id reuse the existing Add logic instead of adding two numbers a second time.

dotnet ef migrations has-pending-model-changes is pinned for a different reason. A small model asked to “check for missing migrations” tends to write a homemade check instead, a grep over the migrations folder or a trial run of dotnet ef migrations add, and you end up maintaining it. The command ships with EF Core, and naming it costs one line.

Everything else stays open. The ef-core-postgres skill covers the NuGet package and the migration commands, and the agent looks up the rest. Where the code goes is settled by AGENTS.md and the service-layer skill. The DbContext, the entity, and the migrations land in backend/Calculator.Persistence. The Values service goes to backend/Calculator.Services, and the endpoints stay in backend/Calculator.Api.

That split is the point. You tell the agent what exists in this environment and what the result has to be. The documentation covers how to get there, and the gate checks the result afterwards.

The database keeps what you put in it

compose.yaml mounts a named volume for PostgreSQL, so rows survive a restart of the container. Your database is not empty after the first run. Later chapters expect the rows you add now to still be there.

This is a long turn for a small model. Expect the model to work for a while. Expect the gate to run, and sometimes fail, before the agent gets to a commit.

16.5 A migration is a generated file

Every file the gate has looked at so far was typed by a person or by the agent. Migrations are not. EF Core reads your entity classes and writes the migration for you. That puts a new kind of file in the repository, and a new kind of failure with it.

A missing migration fails quietly. Add a property to the entity, and forget the migration. The project still compiles, because C# does not know about your database. The unit tests still pass, because none of them looks at the schema. The application starts, sends its first query, and falls over at runtime because the table has no such column. Everything in the repository was green up to that moment.

dotnet ef migrations has-pending-model-changes asks one question: does the current entity model still match the last migration? It answers from the model snapshot that EF Core keeps in the migrations folder. That means it needs no database and no running app. It is fast enough to run after every turn.

That stage does not ask whether the migration is correct; it asks whether the migration is current. Current is the only thing a gate can check about a generated file. A migration that matches the model is wrong only when the model is wrong, and the earlier stages already gate the model.

Every generated file in a project deserves a check of this shape. Lock files, migrations, snapshot tests, and generated code of any kind all share the same weakness. A tool produced them from a source, and nothing notices when the two part ways.

16.6 Make the new stage fail

Never trust a gate you have not seen fail. The agent has committed and the gate is green, so break the new stage on purpose.

The agent chose the file name and the folder for the entity, so find it first. Open it, and add a third int property next to the other two. Add no migration. Then run the gate by hand:

bash scripts/quality-gate.sh
tail -20 quality-gate.log

The last line has to read QUALITY GATE: RED. Read which stage the failing header names. That is the part you are proving, and your agent wrote the wording of that header itself.

If the analyzer stage goes red first, that is warnings-as-errors reacting to a public property with no documentation comment. Give your new property the same kind of comment its neighbors have and run the gate again. Now the migrations stage is the one that fails.

There are two ways back to green. Running git checkout on the entity file throws the model change away. Adding the missing migration keeps it instead. Take the first one here, since the property was only ever a test. In a real run the agent takes the second one, because your gate just told it exactly what was missing.

git checkout backend/Calculator.Persistence  # adjust to your entity's path
bash scripts/quality-gate.sh                # GREEN again
