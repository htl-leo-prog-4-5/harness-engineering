1  From coder to harness engineer

1.1 You type a prompt, and then you hope

You have all used a coding agent by now. You type a prompt and the agent writes code. Then you hope. Maybe you skim the diff. Maybe you start the app once and click around. Some days you just commit it.

Nothing in that loop tells you whether the code works. The agent is not the problem here. Coding agents write reasonable code a lot of the time. The trouble is that “a lot of the time” is a statement about odds. You never see which of today’s changes fell on the wrong side of those odds.

Hoping does not scale. Reading every line by hand does not scale either. The agent produces changes faster than you can read them, and after the fourth file, you stop paying attention.

1.2 What your job is now

So stop thinking of yourself as the person who writes the code. You are a harness engineer now.

A harness engineer sets the guardrails and the quality gates. You decide the architecture and write the rules that everybody follows. You also decide what “done” means before anyone starts. Then you coordinate a team of agents the way a team lead coordinates people. The team members work in parallel and never get tired. But they also never tell you when they are unsure. They do the typing.

That sounds like a demotion until you look at what is left over. Every hard part of software is still yours. You decide what to build, choose the structure it lives in, define correct behavior, and prove that the thing in front of you actually has it. Only the mechanical part moved.

1.3 Agentic engineers, not vibe coders

“Vibe coding” is the popular name for the other way of working. You describe roughly what you want and take whatever comes back. Then you keep prompting until the app looks like it works. It is fun for a weekend demo. It falls apart the first time somebody has to change the result, because nobody, including you, can say what the code is supposed to do.

You are an agentic engineer instead: same tools, different starting point. You know what you want before you type, and you can put it into words precise enough for an agent to act on. Over a single day you move between four familiar roles.

  • Coordinator, splitting work into pieces an agent can finish in one go.
  • Reviewer, reading the diff and the gate output and deciding what ships.
  • Software architect, fixing the structure so the agent has somewhere to put things.
  • Product owner, saying what the software has to do and how you will know.

None of those roles is new. What changed is the fifth role, the one where you sit and type the implementation. That role has largely gone away.

1.4 Probabilistic models, deterministic tools

A large language model, or LLM, samples an answer instead of computing one. Ask the same question twice, and you get two different files. Both are plausible, but sometimes only one of them is correct. That is not a bug you can configure away. Sampling is how the model works.

Two habits follow from that, and this whole course is built on them.

Be specific wherever you care about the specifics. Every detail you leave out is a detail the model picks for you. It picks a fresh one every run. If the project has to use one HTTP client, say so in writing. If test files belong in a certain folder, say so. Vagueness is a coin flip, not flexibility.

Put deterministic tools in the path. A formatter has exactly one correct output for a given file. An analyzer either finds the rule violation or it does not. A test suite passes or fails. It gives you an exit code you can act on. These tools never negotiate, and they behave the same way every time. They also do not care how confident the agent sounded. The model supplies the variety. The tools cut away the part of that variety you refuse to accept.

1.5 What a harness is

Harness engineering is the discipline of building the environment around the agent. It makes good output likely and bad output impossible to miss. The agent is the engine, and the harness is everything else.

Harness element What it does
Context Which documents and rules the agent sees (AGENTS.md, skills)
Tools What the agent can reach: a documentation CLI, the package manager, the database
Gates Deterministic checks the code has to survive: formatter, analyzer, tests
Feedback loops How a failed gate gets back to the agent by itself (a pi extension)

The harness has one rule: never trust the agent. You verify its output, and then you automate the verification. A check you have to remember to run is a check you will skip on the day you are in a hurry.

1.6 The three mechanisms

Three mechanisms carry most of the harness you are about to build. Each one gets a full part of the course later, so one sentence each for now.

AGENTS.md. A markdown file in the project root. The agent reads it before it starts working. It holds the rules, the folder layout, and the commands that are true for this project and no other.

Skills. Folders of instructions. The agent pulls them in only when the task matches. That keeps a long procedure available without paying for it in every single request.

Extensions. Code the harness runs by itself at fixed points in a session, for example when the agent finishes a run. A failing gate then turns into something the agent has to deal with, not something you happen to notice.

1.7 The application you build

Everything in this course is built around one deliberately dull CRUD application. CRUD means the app does little more than create, read, update, and delete records. That is on purpose. When the domain is boring, all the interesting difficulty sits in the harness. That is the part you are here to learn.

  • Backend. .NET 10 with ASP.NET Core Minimal APIs, EF Core, and PostgreSQL, with migrations applied on startup.
  • Frontend. Angular. It reaches the backend through one hand-written API service. That service reads with the httpResource API.
  • Tests. xUnit for the backend and Vitest for the frontend. Playwright drives the end-to-end tier.

Six steps build that up, in order: the backend skeleton, the first deterministic gate, and a database with integration tests and a gate for the migrations it generates. Then comes the Angular frontend with its own toolchain, a skill that teaches the harness a procedure, and linting as the final stage of the gate.

The next chapter introduces the two pieces of the setup you do not build yourself: the coding agent and the model behind it.
