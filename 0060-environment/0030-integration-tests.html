18  Integration tests

18.1 Install the integration test skill

The rules for integration tests come in one more custom skill, from the integration-tests folder in ~/skill-source:

cd ~/work
npx skills add ~/skill-source/integration-tests -y
ls .agents/skills/

web-integration-tests appears next to the earlier skills. It covers the packages, the fixture that starts the API, and how a test class cleans up after itself. It also shows how the fixture moves the tests to a database of their own, which the prompt below asks for.

Tell the agent when to load it. Add this bullet to the ## Layout section of ~/work/AGENTS.md, below the one for the persistence skills:

- Before you write or change an integration test, load the
  `web-integration-tests` skill and follow it, with `Calculator` as `{App}`.

Commit the skill and the new bullet before you prompt:

git add AGENTS.md .agents skills-lock.json
git commit -m "Add the integration test skill"

18.2 The prompt

The backend now stores rows in PostgreSQL, and the unit tests still only cover the calculation logic. Nothing yet proves that a request travels through routing, model binding, EF Core, and the database, then comes back correct. That is what this prompt is for:

Add web API integration tests.

- Use the built-in ASP.NET Core support for integration testing. Look up what
  .NET 10 offers for this.
- Add an xUnit fixture that starts the API in-process. Make sure it applies the
  EF Core migrations before the tests run.
- The tests run against their own database on the PostgreSQL server of this
  environment, never against the development database in PGDATABASE. Name it
  after PGDATABASE with `_test` appended. The tests must not assume it is
  empty, and they must clean up whatever they create.
- Add one integration test. It creates a `Values` entity, lists all ids, gets
  it by id and checks the sum, and finally deletes it.

Commit when the quality gate is green.

18.3 The bullet that does the work

The third bullet is the one that changes how the tests have to be written.

First, it keeps the tests out of the development database. The gate runs the tests after every agent turn, and every run creates and deletes rows. In the development database those rows would sit next to the ones you created with curl, and one careless cleanup filter would delete yours too. A second database on the same server costs nothing: no new container and no new credentials, only a different name. With PGDATABASE=appdb the tests use appdb_test. The web-integration-tests skill shows the fixture how to swap the database, so the prompt only has to state the rule.

The test database can still hold rows, though. It outlives a single run, and every test class in a run shares it. Take a test that expects GET /api/values to return exactly one id. It passes when you run it alone. It fails the moment a second test, or a run that crashed halfway, has left a row behind. The test is not wrong about the code; it is wrong to assume the database is empty.

Writing those constraints into the prompt costs one bullet. Finding the problem later, in a test that fails only in a full run, costs an afternoon.

18.4 Find the pieces in your own code

The agent picked the file names and the class names again, so go look. Four things should be there, and each one is worth understanding rather than just confirming:

git show --stat HEAD
grep -rn "WebApplicationFactory" backend/Calculator.Tests
grep -rn "_test" backend/Calculator.Tests --include=*.cs
grep -rn "partial class Program" backend/Calculator.Api
head -1 backend/Calculator.Tests/*.csproj

A fixture built on WebApplicationFactory<Program>. This is the built-in ASP.NET Core support for integration testing. It boots the whole application in-process and hands the test an HttpClient wired straight into it. You never pick a port or start dotnet run, and the test reaches the app without curl. Open the fixture and confirm it also applies the migrations before any test runs.

A database of its own. The fixture builds a connection string from the same PG variables as the app, with _test appended to the database name, which is what the _test grep finds. It then replaces the app’s DbContext registration with one that uses that connection string. The first test run creates the database, because applying the migrations creates a missing database first. List the databases on the server to see it next to the development one:

psql -d postgres -c '\l'

If only the development database is there after a green run, the tests ran against it. Send the agent back to the web-integration-tests skill.

The test project can name the entry-point type. Top-level statements compile into an internal class called Program, and WebApplicationFactory<Program> references it from another project. Your agent made that legal in one of two ways. The common one is a public partial class Program {} marker at the end of Program.cs, which is what the grep finds. The other is an <InternalsVisibleTo Include="Calculator.Tests" /> entry in the API project file. If the grep comes back empty, check the .csproj before you send the agent back. A green build means one of the two is in place.

The factory depends on one package. The .csproj under backend/Calculator.Tests references Microsoft.AspNetCore.Mvc.Testing. Besides the WebApplicationFactory class, its build targets copy the API project’s dependency manifest into the test output, and that manifest is what lets the factory boot the real app. Whether the Sdk attribute reads Microsoft.NET.Sdk.Web or plain Microsoft.NET.Sdk makes no difference once the package is referenced, so leave that choice to the agent.

18.5 Read the count, not the wording

Run the gate by hand and look at the test stage in quality-gate.log. The summary looks roughly like this:

Passed!  - Failed: 0, Passed: 10, Skipped: 0, Total: 10

Your wording will probably differ. If the agent picked the newer Microsoft.Testing.Platform runner, the same result reads Test run summary: Passed! with the counts on separate lines. The exact number depends on how many unit tests you already had. What matters is that the count went up and that the failure count is 0.

Unit tests and integration tests both run in the same stage, every time an agent run ends. You never opened scripts/quality-gate.sh for this step. The stage calls dotnet test, and dotnet test found the new tests on its own.

A gate defined in terms of the toolchain grows with the project. A gate defined as a list of test names does not.
