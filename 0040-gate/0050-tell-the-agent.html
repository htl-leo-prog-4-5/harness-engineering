15  Tell the agent

The agent still does not know that scripts/quality-gate.sh exists. So it invents its own verification, decided fresh every turn: a dotnet build here and a dotnet test there, or nothing at all. Give it the script you own as the entry point instead.

The note also has to say when not to run the gate. If the agent runs it as its last action, the extension runs the whole gate again right after, and every check runs twice.

15.1 Add the section to AGENTS.md

Type this into AGENTS.md yourself, at the end of the file:

## Quality gate

`bash scripts/quality-gate.sh` runs format, analysis, and tests. The verdict is
the last line of `quality-gate.log`.

The gate also runs by itself when your run ends, from the project-local pi
extension in `.pi/extensions/`. A red verdict comes back to you as a follow-up
message, and you fix it before you are done.

- Run it after an intermediate step of a longer task, to catch problems early.
- Do not run it as your final action. It runs automatically when your run
  ends, and it is slow.
Tell the agent about every automation you add

Each stage you add to the gate is one more check the agent might run by hand, right before the extension runs it again. Whenever you automate something, say in AGENTS.md that it exists and is already handled.

15.2 What this step taught you

The gate now runs after every agent turn, whether the agent wants it to or not. The verdict is a string in a file and an exit code rather than a paragraph of self-assessment. A red verdict comes back into the session and puts the agent back to work. That is a deterministic gate with a closed loop. You built it from one script and one extension, and you never wrote a line of either.

The gate you just built has four gaps.

Nothing prevents a red commit. The gate checks only after the commit already happened. It cannot block anything before that point. When the agent commits and the gate goes red, that commit is already in your history. The loop then fixes the code with a second commit instead of stopping the first one.

The gate is slow. It runs after every turn, even for a one-line change. A full run already takes minutes. EF Core and Angular make the build slower, and Playwright makes the test run longer.

The gate only covers the backend. It skips linting and frontend tests. It has no integration tests and no database.

TreatWarningsAsErrors with every style rule enabled is brutal. It turns every style opinion into a build failure. The rest of the course has to find where a gate that strict costs more than it saves.

Those gaps are the agenda for the rest of the course.

15.3 Where you stand

Harness element After the context part After this part
Context AGENTS.md plus three skills unchanged
Tools mslearn CLI, dotnet, git unchanged
Gates none, the agent decided format, analysis, and tests, always
Feedback loop you, reading a summary automatic, the agent fixes red before it stops

All four elements now exist, but none of them is finished. The next part gives the backend a real database. It also gives the gate a fourth stage, one that catches a kind of problem no compiler and no test will ever report. That problem is a generated file that no longer matches the code it was generated from.
