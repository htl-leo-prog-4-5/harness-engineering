26  Write a skill

26.1 The procedure lives in your head

You built a Playwright end-to-end suite in the frontend part, and one npm script runs the whole thing. But that knowledge is not written down anywhere an agent will find it. You know which command starts the suite. You know that the backend and the Angular dev server both have to answer before the first test runs. You also know what to do when a port is still held by a server you forgot to stop. All of it lives in your head, and in a README nobody loads.

Ask an agent to “run the e2e tests” and it improvises. It starts a server here and forgets to stop one there. A stray dotnet run holds port 5074 for the rest of the afternoon.

A skill is where a procedure like that belongs. You have installed ten of them by now, and the chapter “The cutoff problem” showed how they load: the description sits in the agent’s context on every turn, and the body only when a task matches. So the body can be as long and as specific as the procedure really is.

The agent has also written one for you already. The Angular prompt in the frontend part asked for an api-access skill as one bullet in a long list. Now write one deliberately, as the whole task.

26.2 The prompt

Write a project skill that describes how to run the end-to-end tests: starting the
backend, starting the frontend, running the Playwright suite, and stopping
everything again afterward.

Read the `writing-for-agents` skill first and follow it. This document is written
for an agent, not for a human.

Put it in .agents/skills/e2e-tests/SKILL.md. Commit when the quality gate is green.

The second paragraph is what changes the output. Drop it and you get a README: background, then the command you need buried in the middle. The prompt sends the agent to writing-for-agents and tells it who the reader is. That turns the output into a document an agent can follow.

26.3 Read it like a harness engineer

Open .agents/skills/e2e-tests/SKILL.md and check it for four things. The examples below show what good looks like. Yours will read differently, so use them as the standard, not as the expected answer.

A description that names the situations. The description is the only part of a skill that sits in the agent’s context on every turn. It decides whether the body is ever opened. A description that says what the skill is fires when the agent happens to think of it. A description that names the situations fires when those situations happen. A good one ends with something like “and when a run fails because a URL is already used by a leftover server”. That is a second situation, and a less obvious one. Read your description and ask which situations would make an agent open this file. If the only answer is “when someone asks to run the e2e tests”, it is too narrow.

Steps with completion criteria. Not “run the tests”, but “done when the exit code is 0 and the list reporter shows every test passed”. An agent needs to know when it is finished. If you do not tell it, it decides for itself and usually stops too early.

A failure section. An agent can often improvise a success path but not a recovery path. That’s why failure modes are the part of a skill it cannot invent. A good one documents the “port already used” case together with its fix, pkill -f 'ng serve'. This is the item most likely to be missing from your file. Your agent wrote the skill without ever watching the suite fail, so it had nothing to document. An absent failure section is a finding. Write the section yourself from what you know, or ask for it in a follow-up prompt.

Rationale for the constraints. Whatever constraints your Playwright config carries, the skill has to say why they are there. A skill that only repeats a setting adds nothing the config file does not already say. If your config pins one worker, the skill owes you the reason. A good one reads: “Sequential by design (workers: 1): the tests share the real database.” Yours may run more workers and carry different constraints. The same question applies to each of them. Without the why, a future agent helpfully turns parallelism back on and the tests fight over the same rows. You then spend an afternoon on intermittent failures.

Compare the e2e skill with the api-access skill

Open .agents/skills/api-access/SKILL.md, the one the Angular prompt asked for. One file describes a procedure, and the other describes a convention. Both are useful for the same reason. They say when they apply and how the thing they cover fails.

Fix what the review finds before you move on. A skill you have read and corrected is one you can start calling on purpose.

26.4 Force it and watch

A skill normally loads when the agent decides it is relevant. Forcing it is how you find out whether the one you just wrote works. In pi, type:

/skill:e2e-tests

Whatever you type after the command name is handed to the skill as the request:

/skill:e2e-tests only the values spec

You watch the agent follow your own steps instead of guessing whether the description would have fired. Where it improvises, the skill is missing a step. Fix the file, run /reload so the session picks up the change, and force it again. The forced skill also turns a procedure into a command you can call by name instead of a document you have to reread.

26.5 What this step taught you

Skills are how a harness remembers procedures. AGENTS.md loads on every turn, so it can only hold what is always true. A skill loads when it becomes relevant, so it can carry detail that would be waste in AGENTS.md: the exact commands, the failure modes, and the reason each constraint exists.

The description decides whether the skill is read. A perfect procedure behind a vague description does nothing, so spend your editing time on the one line that sits in context on every turn.

The harness now writes parts of itself. You used an agent, guided by a skill about writing for agents, to write a skill for agents. The agent produced a draft, and you made it complete by checking it against the four things a skill needs: triggers in the description, completion criteria in the steps, a failure section, and rationale for the constraints.

The frontend still has no gate. The backend has had a formatter and a static analyzer since the quality gate part, and the frontend has neither. That is the next thing to fix, and then you can measure what the whole gate costs you.
