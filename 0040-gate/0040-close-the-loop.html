14  Close the loop

The extension is written and committed. You loaded it into a fresh session. Everything you know about it so far comes from reading it. Reading does not tell you whether it works.

14.1 An untested gate is worse than no gate

Keep this rule in mind

An untested gate is worse than no gate. It gives you confidence you have not earned. A gate you have never watched fail is a green light with no bulb in it.

The rule applies to the extension’s two behaviors, and you have to see both. It runs the gate and stays quiet when the code is fine. It puts the agent back to work when the code is not. Test green first, because it is the cheaper experiment.

14.2 Prove the green path first

Commit, so the working tree is clean and the gate is green. Then start pi and give it a prompt with no work in it at all:

Reply with the single word ok. Do not use any tools.

The agent answers ok, and that is the entire session output. You see no gate banner and no verdict line, and the agent never gets a second turn. From the transcript alone you cannot tell whether anything ran.

It is running, though. The gate takes a minute or two after ok comes back, and none of that shows up in the session. Give it that long, then leave pi and look at the log instead:

ls -l quality-gate.log
tail -1 quality-gate.log

The timestamp on the file moved to a few seconds ago, and the last line reads QUALITY GATE: GREEN. The format stage ran, then the build, then the tests. All of that happened on a prompt that did nothing. The harness stayed quiet about it.

Silence is the green state, and that is a design decision you should copy. A message the agent reads on every turn, and can never act on, is noise in the context window. A gate that announces good news is a gate people stop reading.

14.3 Break the code by hand

Now make the gate fail. Open the class that adds two numbers. You found its file when you reviewed the first commit in the context part, so go to the same file now.

Indent the return line by four extra spaces and delete the spaces around the + operator. Save it, and leave the working tree dirty.

You break the code by hand rather than asking the agent to write sloppy code on purpose. Models are trained to produce clean code, so they tidy up even when you tell them not to. Ask for broken code and you spend the experiment arguing about whether the code was actually broken.

14.4 Read the evidence

Before you let the harness see it, run the gate yourself and read what it says:

bash scripts/quality-gate.sh
tail -30 quality-gate.log

The gate stops at the first stage that fails, the property you checked when you read the script. A formatting break never gets as far as the analyzer or the tests, so the format stage is the one complaining.

Your file names differ from everyone else’s, and so do your line numbers and rule ids. Two properties of the output are the same for everyone.

Every finding carries a file, a line and column, plus the rule that fired. That is machine-readable evidence rather than an opinion. You can grep it and count it. You can also hand it to another program, which is exactly what the extension is about to do next.

Nothing in this log is advisory. A warning is something an agent can report and then ignore. Every line in this log belongs to a stage that failed. That stage failed because the tool it ran returned a non-zero exit code. In the build stage, TreatWarningsAsErrors does the work: a style violation becomes an error, and dotnet build fails. The script stops there.

The last line of the file is the verdict, QUALITY GATE: RED, with nothing after it.

14.5 Watch the loop close

Start pi again and send the same empty prompt as before:

Reply with the single word ok. Do not use any tools.

Then take your hands off the keyboard. This one takes several minutes, because the gate runs twice. Watch this sequence happen, with no human input:

  1. The agent replies ok and its run ends.
  2. The extension runs the gate. The verdict comes back RED.
  3. The tail of quality-gate.log goes into the session as a follow-up message.
  4. The agent starts working again, finds the over-indented line and the missing spaces around the +, and fixes the file.
  5. That run ends, and the extension runs the gate again. This time it comes back GREEN.
  6. The session goes quiet, with a clean working tree.

The agent’s last message claims the fix in its own words. Leave pi and check that it is telling the truth:

tail -1 quality-gate.log
git status --short

Stop and appreciate what just happened. Nobody asked for that repair. You did not read the log, and you did not paste it into a prompt. The agent never decided that this change was worth checking. A file in .pi/extensions/ ran a script. The script compared a number to zero, then put the failure back in front of the agent.

Suppose nothing happens after ok, and the log still holds the RED verdict you produced by hand. Then the extension never loaded, or it listens on the wrong event. Restart pi and re-run the grep commands from the “Automate the gate” chapter. A fresh timestamp on the log with no follow-up points to the wrong event. An old timestamp means nothing ran at all.

Suppose instead the log says GREEN while the file is still broken. Then the script is setting the verdict to GREEN before it captures the build output. Re-run bash scripts/quality-gate.sh by hand and read what it wrote.

14.6 What the loop costs

The agent does not stop when you think it stopped. A red gate spends another turn and a few more minutes of gate runtime, without you asking for either. On a clean run you never notice. On a bad one you come back to a session that has been arguing with itself.

The repair and the original change land in the same session. You want to read a diff at the point where the agent finished. But by the time you look, two more commits may already sit on top of it. Read git log before you read the code.

A gate that can never go green never stops. The agent sees RED, and the extension sends a follow-up. The agent tries again, but the gate stays RED, so the cycle repeats. The extension needs a hard limit on consecutive retries, a retry ceiling.

14.7 The retry ceiling

The loop assumes the agent can fix what the gate reports. Sometimes it cannot. A stopped PostgreSQL container makes the gate go red for a reason that has nothing to do with any line of code. No C# edit will bring it back to green. An extension that answers every red verdict with a follow-up message would sit there retrying until you kill it.

So find out whether your extension has a ceiling:

grep -rniE "max|consecutive|attempt|count" .pi/extensions/

A working extension stops after three consecutive red verdicts. It resets the counter when a session starts, and it shows a warning once when it trips. The prompt did not ask for a ceiling, so your agent’s version might not have one.

If your grep comes back empty, prompt for a ceiling:

The quality gate extension keeps sending follow-up messages as long as the gate
is red, which never ends when the failure is not something the agent can fix.
Add a ceiling: after three consecutive red verdicts, stop sending follow-up
messages and show a warning instead. Reset the counter when a session starts and
whenever the gate comes back green.

Restart pi afterwards, because extensions load at session start.

Three wasted turns and a warning make a bad afternoon. An unbounded repair loop against a stopped database makes a bad week.
