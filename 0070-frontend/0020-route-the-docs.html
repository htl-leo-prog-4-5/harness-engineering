21  Route the docs

21.1 Four overlapping sources need a router

Four documentation sources are worse than one unless the agent knows how to choose between them. Ask about IEndpointRouteBuilder, and Context7 answers right away, with docs that may or may not match your .NET version. Ask Microsoft Learn about Angular signals and you get nothing useful at all. The sources overlap in some places and miss each other completely in others. So routing each question to the right source is now part of your harness.

Part of that routing is already in place. The ## Layout section of AGENTS.md names a project skill for each kind of backend work: minimal-api-endpoints for endpoints, service-layer and ef-core-postgres for services, entities, and migrations, and web-integration-tests for integration tests. Those skills say how this repository does something. The documentation sources answer a different question: what a library offers in the version you have installed. The two can disagree. Microsoft Learn’s Minimal API tutorial injects the DbContext straight into the endpoint handler, which is exactly what your service-layer skill forbids. So the routing also has to say which one wins.

There’s a second problem too. It’s about the file itself. Agents write padded, hedged prose, the kind that reads fine and instructs badly. AGENTS.md is loaded into context on every turn, so a wasted word is paid for again on every turn. The writing-for-agents skill teaches the agent to write a document whose reader is another agent, not a human.

So the prompt below asks for two things at once. Route the documentation sources, and write the routing in a form that costs almost nothing to load. The project skills stay where they are, under ## Layout.

21.2 The prompt

Rework the "Up-to-date documentation" section of AGENTS.md.

You now have several documentation sources, and that section must tell you which
one to use when:

- .NET, C#, EF Core, ASP.NET Core: the `microsoft-docs` skill.
- Creating the Angular application: the `angular-new-app` skill.
- Before writing a larger piece of Angular code: read the `angular-developer`
  skill first.
- Any other detail, API signature, configuration option or how-to, for any
  library: the `find-docs` skill (Context7).

The "Layout" section already says which project skill to load for which backend
task. Do not repeat those skills in this section. Add one rule instead: when a
project skill and the documentation disagree, follow the project skill. It says
how this repository does something, and the documentation only verifies the API.

Read the `writing-for-agents` skill first and follow it. AGENTS.md is written for
an agent, not for a human, and it is loaded on every single turn.

Change only the "Up-to-date documentation" section. Leave the ".NET Project
conventions", "Layout" and "Quality gate" sections and every line in them
exactly as they are.
Do not make the file longer than it has to be.

What comes back should be a routing table, not an essay. Roughly this shape:

## Up-to-date documentation

Verify any API, project file property, configuration option or CLI flag in
the docs before using it:

- .NET, C#, EF Core, ASP.NET Core: the `microsoft-docs` skill.
- Creating the Angular app: the `angular-new-app` skill.
- Before writing a larger piece of Angular code: read the `angular-developer` skill.
- Any other library: the `find-docs` skill (Context7).

A project skill named under `## Layout` wins over the documentation. It says how
this repository does something, and the documentation only verifies the API.

Your wording will differ. What matters is that a reader can answer “which skill do I load for this question” right away, without a paragraph of preamble. Backend work hits two lines: the project skill from ## Layout for the shape of the code, and microsoft-docs for the API it calls.

21.3 Read the diff, and read it for deletions

You just told an agent to rewrite a file that governs every future turn. Look at what it actually did:

git diff AGENTS.md

Two things to look for.

Did the other sections survive? The prompt names .NET Project conventions, Layout, and Quality gate by their headings and says to leave them exactly as they are. “Keep the existing conventions” is not precise enough on its own. An agent can read “conventions” as “the documentation rules” and then drop your .slnx rule and your C# 14 extension(...) rule. It may still report that it kept everything. A rewrite prompt without an explicit protection clause is a prompt that silently deletes things.

## Layout is the section most at risk here, because its bullets name skills too. An agent asked to route skills likes to pull them into the new section, or merge them into one list. List every line that names a skill:

grep -n "skill" AGENTS.md

The four backend skills still have to sit under ## Layout, each with the task that loads it. The documentation section names microsoft-docs, the two Angular skills, and find-docs. A backend skill showing up there is a duplicate that the next rewrite will let drift apart from its original.

What else disappeared? Read every line the rewrite dropped, not only the ones the protection clause covers. One line that’s likely to disappear is the note “there is no MCP server in this container, so use the CLI fallback.” The microsoft-docs skill documents its own fallback, so dropping that note is defensible. But it was a line you wrote on purpose, and now it’s not there. Decide whether you want it back, and add it yourself if you do. The same question applies to every other dropped line.

When an agent rewrites a file, git diff is not optional

A summary of a rewrite is written by the thing that did the rewriting. It reports what the agent believes it did, not what landed on disk. The diff is the only account of the change that nobody had a reason to polish.

21.4 Pin a library id when the agent keeps guessing an old version

The routing table sorts questions by topic. You can route one level deeper and pin a single library. One library in this project has earned it: xUnit. In the quality gate part, the agent lost turns on xUnit v3’s new test runner. A small model knows the old xUnit v2 idioms far better than v3. The v3 answers live on xunit.net, which Microsoft Learn does not cover.

Watch what happens when the agent asks Context7 for xUnit. Run the resolution step yourself:

npx ctx7@latest library xunit

You get four Context7 library ids for the same project. One is the documentation website. Another is a snapshot of the API reference pinned to one v3 release. The last two are mirrors of the GitHub repository. All four look plausible. Which one the agent picks is a fresh decision on every run. By now you know what to do with a decision like that: take it away. Try the website one, with a question you already know the answer to:

npx ctx7@latest docs /websites/xunit_net "what changed in the v3 test runner"

Read a screenful of what comes back. That’s current v3 documentation, the material the model’s training data does not have.

Now pin it. Add one line to the routing list in AGENTS.md, by hand, the same way you added the quality gate section there:

- xUnit v3: the `find-docs` skill with the Context7 library `/websites/xunit_net`.

The same move applies beyond this project. When the model keeps guessing an outdated version of one specific library, pin that library’s documentation source by id in AGENTS.md. It’s the same trick as pinning the folder layout in the first chapter of the course. It turns a choice the agent would otherwise make fresh every run into a choice made once, in the harness.
