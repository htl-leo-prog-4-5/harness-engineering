17  The harness pays off

17.1 Read the commit before you read the code

The agent has committed the persistence work. Before you open a single source file, look at what went into that commit:

git show --stat HEAD

Sort that list into two piles. One pile is what the prompt and AGENTS.md asked for: the two new projects with the entity, the database context, and the migration files EF Core generated, the Values service, and the new API module. The other pile is everything the prompt does not explain. Read that second pile first. Every file in it is either the harness at work or the agent acting on its own. You want to know which, before you trust the commit.

This commit may have such a file, and it is .editorconfig. Generated code collides with strict style rules. The migration generator writes a byte order mark at the top of each file it produces, and dotnet format --verify-no-changes rejects it. So the gate goes red on code the agent generated but never typed. The extension feeds that failure back into the session. The agent has to deal with it before it can stop. Nobody typed a word about formatting.

That is the harness paying off. Read what the agent decided to do about it:

git diff HEAD~1 -- .editorconfig

The fix you want to see is a scoped section that relaxes the rule for the migrations folder and nothing else. Exempting generated code is the one defensible version of “switch the rule off.” The rule from the “Own the configuration” chapter still holds: the agent does not make that call in silence. Check the scope, not just the intent.

Not every run ends up in this exact situation, so your commit may leave .editorconfig untouched. The ef-core-postgres skill tells the agent to run dotnet format right after it generates a migration, and that run may already repair the file before the gate sees it. The two piles still apply. Whatever sits in your second pile, chase it down the same way: the diff, the gate log, or a direct question to the agent. A change nobody asked for is not automatically wrong, but it never gets to stay unexplained.

17.2 What to check in the diff

Now read the code. The agent chose the file names and the folder layout on its own, and it named the classes. Start by finding out what it made:

git show --stat HEAD
grep -rn --include=*.cs "MigrateAsync\|Migrate()" backend/Calculator.Api
grep -rn --include=*.cs "PGHOST\|Npgsql\|UseNpgsql" backend
grep -rn --include=*.cs "DbContext" backend/Calculator.Api/Endpoints

Check four properties, and each one tells you where to look.

Endpoints call services. The last grep has to print nothing. An endpoint in Calculator.Api takes a service interface from Calculator.Services and never the DbContext itself. A hit means the agent skipped the service layer for that endpoint, so send it back to the service-layer skill.

Migrations run on startup. Program.cs has to apply pending migrations before the app starts serving requests. It usually does that with a call to MigrateAsync() on the context’s Database facade. Without it, the first request hits tables that do not exist yet.

The connection comes from the environment. The five PG variables hold the connection details. If you find a full connection string sitting in appsettings.json, the agent hard-coded the credentials instead. The prompt told it to read them from the environment. That setup breaks on any machine with a different database.

Get by id reuses the existing logic. The sum in the response has to come from the Add method, which already has unit tests. With the service layer in place, Add moves out of the endpoint file into a service in Calculator.Services. If you find left + right written out a second time inside the new service or endpoint, the agent duplicated that logic. Say so and make it redo that part.

17.3 Try it for real

Reading the diff is not the same as seeing the API work. Start the API in the container shell:

dotnet run --project backend/Calculator.Api/Calculator.Api.csproj

Then, in a second terminal inside the container:

PORT=<the port it printed>
# create one, and keep the id it gives back
ID=$(curl -s -X POST localhost:$PORT/api/values \
      -H 'Content-Type: application/json' \
      -d '{"left":17,"right":25}' | grep -o '"id":[0-9]*' | cut -d: -f2)
curl -s localhost:$PORT/api/values          # a list of ids, yours among them
curl -s localhost:$PORT/api/values/$ID      # {"id":…,"left":17,"right":25,"sum":42}
curl -s -o /dev/null -w '%{http_code}\n' -X DELETE localhost:$PORT/api/values/$ID

That block captures the id from the POST response instead of assuming 1. The database is shared and keeps whatever earlier runs left in it. So the row you just created is almost never the first one.

The field names are the second detail to watch, and they can trap you. If your agent named the JSON fields something other than left and right, the POST does not fail. ASP.NET Core binds the unknown fields to nothing. It cheerfully stores a row of two zeros and returns 200. So check the response body, not the status code. When {"id":…,"left":0,"right":0,"sum":0} comes back, open the API module the agent wrote for Values. Read the names it actually chose. That file also carries the real route if the agent did not pick /api/values:

grep -rn "MapPost\|MapGet\|MapDelete" backend/Calculator.Api --include=*.cs
