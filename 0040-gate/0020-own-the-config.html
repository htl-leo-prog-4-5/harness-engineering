12  Own the configuration

The agent just wrote three pieces of harness for you: the MSBuild settings that turn analysis on, the .editorconfig that holds the style decisions, and the gate script at scripts/quality-gate.sh. In a few minutes you’ll trust those three files to tell you whether your code is acceptable. So read them first.

Start by finding out what actually changed:

git show --stat

Open every file in that list. The sections below tell you what to look for in each one. Your files will not match another run’s word for word, and they don’t have to. What has to match is the effect.

12.1 The build has to turn warnings into errors

MSBuild automatically picks up a file named Directory.Build.props from the folder tree above a project. That makes it the natural place for settings that apply to the whole solution. Look for that file first. If the agent put the properties into the individual .csproj files instead, that works too. You just have more places to keep in sync.

There is more than one correct way to write these settings. Read your file for the four effects in the table, not for the exact property names. AnalysisLevel=latest-recommended and AnalysisMode=Recommended are the same decision spelled differently. “All style rules as warnings” is often a dotnet_analyzer_diagnostic.category-Style.severity = warning line in .editorconfig.

Effect you are looking for One way to write it
The recommended CAxxxx code-quality rules are on AnalysisMode=Recommended
All IDExxxx code-style rules are on AnalysisModeStyle=All
Style rules run during dotnet build, not just in the IDE EnforceCodeStyleInBuild=true
Any warning fails the build TreatWarningsAsErrors=true

People miss the third row. Style rules are an IDE feature by default. Without EnforceCodeStyleInBuild, your IDExxxx findings never reach the build output, so a gate that runs dotnet build never sees them. If you cannot find that effect anywhere, search for it:

grep -rn "EnforceCodeStyleInBuild\|TreatWarningsAsErrors" --include=*.props --include=*.csproj .

If that grep prints nothing, the gate you are about to turn on is weaker than the prompt asked for. Send the agent back before you continue.

12.2 The editorconfig is where cheating shows up

.editorconfig holds the concrete style decisions: indentation, brace placement, var usage, and the order of using directives. Microsoft’s C# language rules documentation describes every option in the file. The agent should have read that page while writing it.

It is also the first place to check for cheating:

git diff HEAD~1 -- .editorconfig backend/Directory.Build.props | grep -i "severity = none"

Any severity = none in that diff is the agent deciding which rules you get without telling you. Some of those decisions are fine. Test method names genuinely break CA1707, the rule about underscores in identifiers. Turning it off for the test project is a fair choice. But you make that decision, not the agent, and only after it has told you why. A rule switched off in silence is a rule you will never think about again.

Review the code the agent changed

Read the C# source diff as well as the configuration. The agent may have replaced file-scoped namespaces with block-scoped ones (IDE0160). Look for expression-bodied methods rewritten with block bodies (IDE0022), and var replaced by explicit types (IDE0008).

Decide whether those changes match your team’s preferences. You can keep the style or declare a different preference in .editorconfig. Explain your decision before asking the agent to apply it. A green gate proves the code follows the configured rules; you still have to choose those rules.

Allowing either var or an explicit type requires a separate decision. IDE0007 enforces var, and IDE0008 enforces explicit types. To accept both, disable both diagnostics in the intended scope and explain why.

12.3 The gate script

scripts/quality-gate.sh is the file you will read most often, so read it now while it is small. It runs the three stages in order and writes everything to quality-gate.log.

Check four things in your version.

The format stage only checks. The prompt asked for verify mode, so the script should pass something like --verify-no-changes to dotnet format. A gate that fixes the formatting itself reports green and teaches the agent nothing.

The last line is the verdict, with nothing after it. No timestamp and no row of dashes. In later chapters, other programs read that verdict, and any trailing line breaks them.

The script stops at the first failing stage. You want the first problem, not every failure that follows it. A later chapter relies on the log holding only the stage that failed. If your script runs all three stages whatever happens, send the agent back.

The exit code follows the verdict. Run it yourself and look:

bash scripts/quality-gate.sh; echo "exit code: $?"

Right now, on committed code, it should print 0. Break a file and it has to print something else. The automation you add in the next chapter decides green or red from that number alone. A script that always exits 0 gives you a gate that can never fire.

Why one script and not three commands in the harness

Nothing forces the checks into a script. Whatever runs the checks could run dotnet format, dotnet build, and dotnet test separately. Putting them in one file gives you a single verdict and a single log. You can also run the same gate from your shell and later from a build server. A gate that only exists inside the agent’s session cannot be rerun when it fails.
