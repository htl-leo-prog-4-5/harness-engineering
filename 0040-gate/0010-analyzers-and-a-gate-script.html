11  Analyzers and a gate script

Right now the agent decides whether your code gets formatted and whether the analyzers run. It decides whether the tests run too. The same prompt leads to a different decision on a different day. When the agent does run the tests, you learn the result from a summary the agent writes about its own work.

A check that only runs when the agent chooses isn’t a gate, because a gate runs every time. The agent might run it today, but that tells you nothing about tomorrow.

11.1 What a real gate has to do

  1. It runs every time, without being asked.
  2. It produces a machine-readable verdict, not prose.
  3. It is hard to satisfy by accident. A warning has to be a failure.

The third requirement matters because a warning is easy to ignore. If a rule violation only prints a yellow line that scrolls past, the agent can honestly report “the build succeeded.” Broken code still sits in the project. Turn the warnings into errors and that sentence becomes impossible to write.

11.2 One script first, then something that runs it

This part builds the gate in two moves. This chapter gives you a shell script that runs the checks and prints a machine-readable verdict, plus a build that treats warnings as errors. The automation that runs the script every time comes later. The script comes first because a gate that only the agent can trigger is miserable to debug, so it has to work from your shell before anything calls it.

11.3 Start this one in a fresh session

Commit first, so git status comes back clean. Then leave pi and start it again, or type /new.

The old conversation is full of dotnet new output and NuGet version lookups from building the skeleton. The agent would carry all of it in its context window through the longest run in the book. Discarding it is safe, because everything the agent needs is in AGENTS.md, the committed code, and git log. None of it lives in the chat.

So here is the rule for the rest of the book: new task, new session. Continue a session while you review what the agent just did or tell it to repair what it got wrong. Start fresh when the task changes.

When a fresh session produces a worse result than a continued one, that is a finding. Something the agent needed was only in the conversation, and it belongs in AGENTS.md instead.

11.4 The prompt

Paste this prompt into the fresh session. AGENTS.md already names scripts/quality-gate.sh, so your first run may have left a small script there. That changes nothing, because the prompt defines what the script has to do and the agent extends or replaces whatever is in place.

Add a deterministic quality gate to this project.

1. Turn on .NET code analysis for every project in the solution: recommended
   analysis mode, warnings treated as errors, and all code style rules reported
   as warnings. Look up how to configure this properly.

2. Put the checks into one single script at scripts/quality-gate.sh. That script
   executes, in this order:
     - dotnet format, verify only, must not rewrite files
     - dotnet build
     - dotnet test
   The script must write the combined output to quality-gate.log in the project
   root. The very last line of that file must be exactly `QUALITY GATE: GREEN`
   or `QUALITY GATE: RED`, with nothing after it, so other tools can read the
   verdict. The script exits 0 on green and non-zero on red.

Do not disable or downgrade any analysis rule to make the existing code green.
Fix the code instead. Commit when done.

11.5 What the prompt does not contain

The prompt carries no MSBuild properties and no .editorconfig rules, and you write no bash in it. It states the requirement, and the agent works out the mechanism from Microsoft’s documentation through the microsoft-docs skill.

Read these two parts of the prompt twice.

The last line of the log file. “Exactly QUALITY GATE: GREEN or QUALITY GATE: RED, with nothing after it” is the machine-readable verdict. Everything you build in the rest of this part reads that string or the script’s exit code.

The ban on downgrading rules. Turning on every style rule makes existing code fail. The fastest way to stop the failures is to switch the rule off. Write that ban into the prompt, or you’ll get a green gate that checks nothing.

Expect this run to take a while, even though a large frontier model would finish it quickly. Treating warnings as errors means that code which built fine a minute ago now has dozens of errors. The agent has to fix every one of them before it can claim success. That’s the gate doing its first run against the code you already have.
